# Run the public reference

This walkthrough demonstrates selected decisions from the production case using fictional documents and identities. It includes a grounded answer, an unsupported question, document access denial, prompt-injection blocking, and operational/audit events joined by request ID.

## Offline HTTP walkthrough

After installing the hash-locked dependencies in the README:

```bash
make walkthrough
```

The script builds a temporary synthetic index, starts the real FastAPI application on a random loopback port, sends five HTTP requests and verifies their event correlations. It removes the temporary index and logs after the run. The generated report is `.local/walkthrough.md`; the checked-in [example report](walkthrough-report.md) normalizes IDs, timestamps and latency for stable display.

| Identity | Server-owned audiences | Effect |
|---|---|---|
| `engineer-demo` | `all`, `engineers` | Can answer the production-access question |
| `reader-demo` | `all` | Cannot read engineering documents, including their titles and source IDs |
| unknown subject | none | HTTP 403 before retrieval |

Removing filters does not remove authorization. Selecting `audience=engineers` as a reader yields a policy refusal with no sources. A body `actor_id` cannot change identity. Documents without an allowed audience are excluded before ranking.

The loopback harness deliberately simulates the trusted proxy header; it is not an Entra authentication test. In the protected deployment, OAuth2 Proxy supplies the authenticated subject. In direct local mode, identity comes only from operator configuration (`RAG_LOCAL_ACTOR_ID`, default `engineer-demo`); request headers and body actor IDs do not grant privileges.

## Reproduce the evaluation

```bash
make eval
make presidio-up
make eval-presidio
```

The suite has 43 cases; three require Presidio and are skipped by the regex backend. The [checked-in offline report](evaluation-report.md) and [live Presidio report](evaluation-report-presidio.md) includes SHA-256 fingerprints of the code, policy, index and cases. Three specified retrieval-quality failures are waived; additional failures and every security/control failure still fail CI. Reports separate observable policy violations, control-contract failures and answer-quality failures. The comparison disables guardrails but keeps authorization enforced.

These are synthetic control checks using an extractive gateway. They do not measure real-model injection resistance or production answer quality.

## Verify the live model boundary

This verification uses the pinned Presidio and LiteLLM containers and an internal synthetic OpenAI-compatible upstream. It requires Docker; it downloads no inference model and sends no content to a hosted provider.

```bash
export LITELLM_MASTER_KEY=$(python3 -c "import secrets; print('sk-' + secrets.token_hex(24))")
export LITELLM_UPSTREAM_BASE_URL=http://test-model:8080/v1
export LITELLM_UPSTREAM_MODEL=openai/synthetic-reference-model
docker compose -f infra/docker-compose.yml --profile gateway --profile verification \
  up -d --wait presidio-analyzer presidio-anonymizer test-model litellm
make verify-gateway
```

The script sends completion calls without selecting guardrails explicitly. It checks that:

- default-on input masking removes a synthetic corporate email and card before the upstream receives them;
- default-on output masking removes the synthetic email generated by the upstream;
- a request containing a US SSN is blocked on the completion route;
- the real RAG HTTP API calls LiteLLM and receives an answer, while reader scope escalation is denied.

The mock upstream is reachable only on the Compose gateway network. It returns a Boolean input-leak marker, never logs prompts and is available only through the `verification` profile. The verifier requires a gateway; an absent gateway is a failure, not a successful skip.

To check the container's internal model route and actual operational-log delivery, keep the same verification environment and run:

```bash
export RAG_GATEWAY_MODE=openai-compatible
docker compose -f infra/docker-compose.yml --profile gateway --profile verification \
  up -d --build --wait rag-assistant loki fluent-bit
make verify-telemetry
```

This matches a real container request ID in the separate audit spool and Loki. Fluent Bit runs with the log owner's UID (`10001`), retains no capabilities and has no audit-volume mount. A network-free initializer grants that UID ownership only of the collector state directory. Loki/Prometheus loopback publishing uses a separate observability access network; the API stays internal.

Stop the verification route when finished:

```bash
docker compose -f infra/docker-compose.yml --profile gateway --profile verification stop rag-assistant fluent-bit loki test-model litellm
unset LITELLM_UPSTREAM_BASE_URL LITELLM_UPSTREAM_MODEL RAG_GATEWAY_MODE
```

Starting the production-style route separately requires a configured approved upstream and gateway key. The RAG container uses `http://litellm:4000/v1`, permitted by an exact operator-owned HTTP host allowlist. Other remote HTTP destinations are rejected and redirects are not followed. The application sanitizes context before outbound HTTP even when a gateway is configured; external-model mode cannot disable application guardrails.

## Protected identity deployment

Compose gives OAuth2 Proxy a separate egress network for Entra discovery/token exchange; the RAG API has no published port. Set `IDENTITY_POLICY_FILE` to a private JSON file following `sample-data/identity-policy.json`, with actual authenticated subject IDs as keys. The Compose secret mounts that file read-only. The fictional IDs deliberately do not grant a real Entra user access by default.

The forwarded-header trust boundary assumes controlled containers and a protected backend network. This is not a signed identity token at the API: a compromised process with backend network access can impersonate the proxy. Production deployment must isolate ingress provenance or validate a token at the application. A disposable Entra registration, real subject mapping and token/callback tests remain a separate live validation requirement.

## Production / reference / roadmap

| Layer | Production experience | Public reference | Reference roadmap |
|---|---|---|---|
| Platform | On-prem gateway, SSO, separately operated services | Compose, optional LiteLLM, two synthetic identity scopes | Real Entra flow and deployment-specific policy mapping |
| Retrieval | Two domain assistants, semantic retrieval, SharePoint sync | Five fictional documents, deterministic vectors, citations/refusals | Semantic embeddings and held-out paraphrases |
| Guardrails | Platform guardrail policy remains in progress | English pattern checks, shared Presidio, regression gates | Trained classifier evaluated on separate adversarial cases |
| Operations | Operational logs to Loki; prompt audit transport to SIEM | Separate event schemas, files and volumes with request correlation | Encrypted SIEM delivery, durable/tamper-evident storage |

Operational events never contain prompt/answer fields. Default audit records keyed hashes and source IDs; `AUDIT_INCLUDE_PROMPT=true` intentionally stores the original prompt only in the restricted audit spool. The reference does not ship SIEM delivery or production-scale availability guarantees.
